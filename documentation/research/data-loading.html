Loading a large session

Opening a CSV for the first time and zooming into 30 seconds of telemetry involve different work. The viewer converts the file once and then reads the requested channel and time range.

How long does the first read take?

The synthetic 100 Hz CSV has 12 Float64 columns and 20 million rows (1.71 GB, decimal). Each engine ran in a new process on the same file using an explicit schema, Zstandard compression and Parquet row groups of up to 65,536 rows.

Library choice. Polars imports CSV files. PyArrow inspects Parquet metadata and reads individual channels. DuckDB is an option for SQL queries across sessions. The incremental Arrow reader used the least memory in this test and is worth evaluating on machines with less RAM.

With 800 display bins, the 20M-row overview returned 1,600 points, about 29 kB of JSON. A close zoom with few samples returns their original values. Peak memory includes native libraries and depends on the workload.

From click to chart. A separate local Chrome test used the 5M-row CSV with the viewer already running. The first plot took 2.53 s from clicking Open file with an empty cache. Reopening took 398 ms. Clicking Apply for the 24,990–25,020 s window (3,001 samples) took 159 ms. These individual timings include HTTP requests, status polling, drawing and browser automation.

From disk to pixels

  1. Stream the CSV once. Use comma-separated UTF-8 with a single header, decimal points and session time in seconds (time_s). An explicit numeric schema avoids first-batch inference and per-row Python objects. Missing channel values remain missing. A missing, infinite or decreasing CSV timestamp stops the import.
  2. Reuse the cache. A worker writes a temporary file and publishes it with an atomic rename after validation. The cache key uses the resolved path, file size, nanosecond modification time and schema version. If a file changes while retaining its path, size and timestamp, remove the corresponding cache entry.
  3. Read native Parquet in place. Each row group is indexed by its minimum and maximum timestamp. If statistics are missing, only the timestamps in that group are scanned. Unsorted data may touch more groups. For new exports, use increasing timestamps and contiguous row groups. A file per sample or very high-cardinality partitions increase overhead.
  4. Read the columns in view. A query reads time and the selected channel in batches of 65,536 rows. Rapid zoom requests are debounced and stale responses are discarded. Display bins keep original samples at their extrema. FFT and statistics use the original data. Gaps break the drawn line and zoom reveals the surrounding samples.
  5. Limit the data sent to the display. A full-range request scans the selected channel and sends a bounded number of points to JavaScript. Read time depends on the amount of data scanned. For larger sessions or many open logs, a stored multiresolution min/max index could trade disk space for faster overviews. The current viewer scans on demand.

Interpreting the comparison

Dell Precision 7720, i7-7820HQ (8 logical threads), 31.9 GiB RAM, NVMe SSD, Windows 10 and Python 3.12.6. Versions were Polars 2.1.0, PyArrow 26.0.1, DuckDB 2.0.1 and NumPy 2.5.5. Fixed run order was Arrow → Polars → DuckDB → viewer pipeline. The application cache started empty. The Windows file cache still held data from writing the synthetic CSV. Each engine used its own threading and Parquet encoding. These measurements apply to this workload and machine.

To reproduce the test, activate the project’s Python environment, install the additional benchmark packages duckdb==2.0.1 psutil==7.2.2 and run python tools/benchmark.py --rows 20000000 --output documentation/research/benchmark-20M.json. The test creates temporary CSV and Parquet files. Raw measurements for both sizes are in the same directory as this study.
